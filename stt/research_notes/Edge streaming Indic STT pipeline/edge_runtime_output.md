# Edge deployment of streaming ASR on laptop-class CPUs (x86 + Apple silicon): runtimes, export, quantization, application layer

Research date: 2026-10-08. Method: web search + page fetches of primary sources (GitHub, HF model cards, arXiv, vendor docs); secondary sources flagged. Anything not directly supported by a fetched source is placed in Inferences or Gaps and labelled as such. Latest sherpa-onnx release visible in the changelog I retrieved was 1.13.8 (shown as "published 27 days ago" on pub.dev, i.e. ~Sept 2026).

## 1. sherpa-onnx: streaming model types, NeMo export/consumption, loader limits, Indic conversions, bindings, license, RTF

### Takeaway
sherpa-onnx (Apache-2.0, 12 language bindings, all desktop/mobile/WASM targets) is the only runtime I found with first-class, versioned support for NeMo cache-aware streaming transducers (Nemotron-speech-streaming-en-0.6b since 1.12.22; multilingual Nemotron-3.5 incl. Hindi since 1.13.3), plus streaming Zipformer transducers (incl. a Bengali Vosk model, Feb 2026) and streaming NeMo CTC. It requires the encoder / decoder / joiner split with injected metadata and is tightly version-coupled to the exporter. No streaming (cache-aware) Indic checkpoint from AI4Bharat exists; the community IndicConformer ONNX conversions are offline.

### Cited Findings
- License Apache-2.0; streaming ASR model families = online transducer, online Paraformer, online CTC; bindings: C++, C, Python, JavaScript, Java, C#, Kotlin, Swift, Go, Dart, Rust, Pascal, plus WASM; platforms Android, iOS, Windows, macOS, Linux, HarmonyOS, Raspberry Pi on x64/x86/arm64/arm32/riscv64; NPU backends Rockchip RKNN, Qualcomm QNN, Ascend, Axera, Intel OpenVINO; also VAD (Silero), punctuation, diarization, speaker ID — [sherpa-onnx GitHub README](https://github.com/k2-fsa/sherpa-onnx)
- Official "online transducer" model index lists only Zipformer (16 entries, incl. `sherpa-onnx-streaming-zipformer-bn-vosk-2026-02-09` Bengali, Chinese 2025-06-30 xlarge/int8, Korean, English 20M/2023 variants, bilingual zh-en), one streaming Conformer (zh) and two LSTM transducers; NeMo is on a separate page (that page 404'd for me) — [sherpa docs: online transducer index](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/index.html)
- Changelog (pub.dev mirror of sherpa-onnx releases), NeMo/streaming-relevant entries: 1.12.8 "APIs for online NeMo CTC models"; 1.12.14 fix TDT decoding for NeMo TDT; 1.12.22 support `nemotron-speech-streaming-en-0.6b`; 1.12.24 modified beam search, hotwords, ys_log_probs for NeMo transducers; 1.13.0 update nemotron-speech-streaming-en-0.6b; 1.13.1 fix bugs in NeMo transducer modified beam search; 1.13.2 export NeMo unified streaming 0.6b + "buffered RNNT streaming path for Parakeet Unified"; 1.13.3 multilingual Nemotron-3.5 streaming ASR support; 1.13.4 C++ runtime + QNN export for nemotron-speech-streaming-en-0.6b, per-stream hotwords in JS; 1.13.5 "Fix greedy search decoding for NeMo streaming transducer" and re-export of nemotron-3.5-asr-streaming-0.6b to ONNX; 1.13.7 populate ys_probs in online NeMo transducer greedy decoders — [sherpa_onnx_linux changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog)
- Repo export scripts under `scripts/nemo/`: `fast-conformer-hybrid-transducer-ctc`, `nemotron-3.5-asr-streaming-0.6b`, `nemotron-speech-streaming-en-0.6b`, `parakeet-tdt-0.6b-v2/v3`, `parakeet-unified-en-0.6b`, `canary`, `qnn`, etc.; no Indic-specific directory — [sherpa-onnx scripts/nemo listing](https://github.com/k2-fsa/sherpa-onnx/tree/master/scripts/nemo)
- Nemotron-3.5 export recipe: `export_onnx.py` (needs NeMo from git main) produces `encoder.onnx` + `encoder.data`, `decoder.onnx`, `joiner.onnx`, int8 variants of all three, and `tokens.txt` converted from the SentencePiece tokenizer; supports 80/160/320/560/1120 ms chunk sizes; encoder metadata contains `prompt_dictionary` and `auto_prompt_id`; language passed as string (`--language=ja`), empty/`auto` = auto-detect prompt — [sherpa-onnx nemotron-3.5 export dir](https://github.com/k2-fsa/sherpa-onnx/tree/master/scripts/nemo/nemotron-3.5-asr-streaming-0.6b)
- Loader expectations learned from a third-party NeMo mirror: encoder must carry k2-fsa metadata else "No model_type in the metadata!"; injected keys were `model_type=nemo_transducer`, `vocab_size`, `subsampling_factor`, `normalize_type`, `pred_rnn_layers`, `pred_hidden`, `feat_dim`; NeMo exports the prediction+joint as one combined graph while sherpa's nemo_transducer loader needs separate decoder and joiner sessions (split at the prediction-network output). This mirror is about offline models but the same loader contract applies — [pantinor/ovos-conformer-mirrors](https://huggingface.co/pantinor/ovos-conformer-mirrors)
- Prebuilt community archives named like `sherpa-onnx-nemo-streaming-fast-conformer-ctc-en-{80,480,1040}ms` and matching transducer archives exist (seen in a HF commit listing; I did not open the archives) — [xumo/onnx_models commit](https://huggingface.co/xumo/onnx_models/commit/1bd73e49eaf99115aeb9365ea1e1a2741a8564e7)
- Hotwords: only transducer models (offline and online); requires `modified_beam_search` (not default `greedy_search`); one hotword per line with optional `:score`; BPE hotwords need `bpe.vocab` (not `bpe.model`), `modeling-unit` must match; boost is cancelled if the partial path never completes the hotword; matching is token-level — [sherpa hotwords docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html). Changelog adds byte-level-BPE hotwords (1.12.18) and per-stream hotwords in the JS API (1.13.4) — [changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog)
- Community IndicConformer in sherpa format: EchoBharat model card points to an Apache-2.0-tagged conversion `parismitaglobalsolutions/indicconformer-sherpa-onnx` (I could not open its README; upstream weights are MIT so "honour both"); its graph is offline: input log-mel [B,80,T] + length, output log-probs [B,T/4,V] with V=5633, NeMo featurizer (25 ms win, 10 ms hop, 512 FFT, 80 Slaney mels, 0.97 pre-emphasis, per_feature normalisation) — [EchoBharat models](https://huggingface.co/RaunakSaha/echobharat-models)
- Upstream AI4Bharat Hindi: hybrid CTC-RNNT Conformer-Large, 120M-param encoder, 17 blocks, d_model 512 (gated HF repo); Telugu analogue is MIT — search-result summary of [ai4bharat hi hybrid_ctc_rnnt_large](https://huggingface.co/ai4bharat/indicconformer_stt_hi_hybrid_ctc_rnnt_large) and [aikosh Telugu card](https://aikosh.indiaai.gov.in/home/models/details/ai4bharat_indicconformer_stt_te_hybrid_ctc_rnnt_large_telugu_automatic_speech_recognition_model.html)
- Published RTF (non-official, third-party): see section 4. I found no official sherpa-onnx RTF table for x86/Apple laptops in this session (sherpa docs "benchmark" pages did not surface). The sherpa-onnx docs claim all models run in real time on a Raspberry Pi 4 (qualitative) — via [search summary of sherpa docs](https://github.com/k2-fsa/sherpa/blob/master/docs/source/onnx/pretrained_models/small-online-models.rst)

### Inferences
- Base-model choice should be constrained to: (a) NeMo cache-aware FastConformer RNNT/hybrid (Nemotron-family or `stt_*_fastconformer_hybrid_large_streaming_*`), or (b) icefall streaming Zipformer transducer. Both have maintained sherpa-onnx loaders. wav2vec2-style and Whisper-style models have no streaming loader in sherpa-onnx (Whisper is offline there; "simulated streaming" with VAD only).
- Because sherpa's NeMo loader has had streaming-specific bug fixes through 1.13.5-1.13.7, pin sherpa-onnx >= 1.13.5 (OpenWhispr says >= 1.13.4 is required; changelog shows a greedy-search fix for NeMo streaming transducers only landed in 1.13.5 — see section on export pitfalls).
- Hotwords are unavailable if you choose CTC-only or if you deploy greedy decoding for latency; to get hotwords on Indic you need a transducer + modified_beam_search and the same SentencePiece vocab, which costs CPU (not quantified in my sources).

### Gaps
- Official sherpa-onnx NeMo streaming doc page (404 at the URL I guessed) and the real documented list of loader limitations; endpoint-rule doc (`endpoint.html` 404). No source found for whether sherpa-onnx supports cache-aware streaming TDT (only offline/buffered TDT found).
- Contents/streaming status of `parismitaglobalsolutions/indicconformer-sherpa-onnx`; I could not read its README.
- No official sherpa-onnx RTF table for i5/i7/Ryzen/M-series.

## 2. Other runtimes: ONNX Runtime direct, OpenVINO, CTranslate2/faster-whisper, whisper.cpp, MLX/mlx-audio, CoreML, ggml/GGUF ports, NeMo export, Moonshine, Kyutai

### Takeaway
Direct ONNX Runtime (with three-session encoder/decoder/joiner and custom cache/feature code) is viable and Microsoft ships it, but you write the streaming state machine yourself. Whisper-family runtimes (whisper.cpp, faster-whisper) are not true streaming and Whisper is very weak on Telugu/Hindi zero-shot. Kyutai (1B en/fr only) and Moonshine (no Indic) don't cover the languages. For Apple silicon, CoreML/MLX ports of Nemotron-3.5 (Hindi included) exist but publish no RTF.

### Cited Findings
- **ONNX Runtime direct (Microsoft):** Nemotron-0.6B cache-aware FastConformer rebuilt as three ONNX sessions (encoder, LSTM decoder, joiner) so each can be quantized separately; NeMo-compatible log-mel front end implemented natively with a ring-buffer pre-encode cache; encoder rolling cache tensors updated in place; decoder LSTM h/c persist; RNNT greedy as a state machine; MHA fused into one kernel gave a significant encoder speedup; shipped via Foundry Local / ONNX Runtime GenAI SDK (C#, Python, JS, C++, Rust) — [arXiv 2604.14493 (HTML)](https://arxiv.org/html/2604.14493)
- **ONNX/Olive conversion of Nemotron-3.5:** a community repo converted `nemotron-3.5-asr-streaming-0.6b.nemo` with Microsoft Olive into cpu/ (fp32 decoder+joint, int4/int8 encoder), gpu-cuda/, gpu-dml/ variants; no sizes/WER/cache-tensor details given; license "other / see NVIDIA license" — [DimQ1/nemotron-speech-onnx](https://huggingface.co/DimQ1/nemotron-speech-onnx)
- **OpenVINO:** FluidInference published Nemotron-3.5-ASR-Streaming-Multilingual-0.6B as OpenVINO IR (FP32/FP16/INT8 weight-only encoder, per-channel symmetric; claims INT8 WER matches FP32 on FLEURS; targets CPU/Intel NPU/iGPU; snippet had no RTF) — [FluidInference Nemotron OV](https://huggingface.co/FluidInference/Nemotron-3.5-ASR-Streaming-Multilingual-0.6b-ov). Parakeet-TDT-0.6B-v2 OV card: RTFx 37.8 (NPU) and 5-8 (CPU) on Core Ultra 7 155H, but that pipeline uses 10 s chunks with 3 s overlap (chunked, not cache-aware streaming) — [FluidInference parakeet OV](https://huggingface.co/FluidInference/parakeet-tdt-0.6b-v2-ov). sherpa-onnx also lists Intel OpenVINO NPU support — [sherpa-onnx README](https://github.com/k2-fsa/sherpa-onnx)
- **GGUF/ggml:** `cstr/nemotron-3.5-asr-streaming-GGUF` for CrispASR (`--backend nemotron`, streaming via `CRISPASR_NEMOTRON_STREAMING=1`): F16 ~1.3 GB, Q4_K 458 MB (pre-encode weights stay F32), Q4_K ~2x faster than F16; license OpenMDW-1.1; no RTF given — [cstr GGUF card](https://huggingface.co/cstr/nemotron-3.5-asr-streaming-GGUF). NVIDIA's own `NeMo-Speech.cpp` (q8_0 GGUF) container targets CUDA GPUs, with no published CPU RTF — [NGC NeMo-Speech.cpp](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/nemo-speech.cpp) and [Nemotron-speech-streaming-en card](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b)
- **Apple (CoreML + MLX):** multilingual Nemotron runs on CoreML (ANE) and MLX; CoreML INT8 612 MB disk / 1238 MB streaming peak (M5 Pro); MLX bf16 1217 MB / 1474 MB; MLX 8-bit 733 MB / 992 MB; MLX 5-bit 539 MB / 800 MB (default); MLX 4-bit 473 MB / 747 MB (research export, larger quality loss); avg FLEURS WER over six languages 11.53 (5-bit) vs 11.01 (8-bit); chunk options 80/320/560/1120 ms (320 default); no RTF — [soniqo.audio Nemotron guide](https://soniqo.audio/guides/nemotron)
- **mlx-audio:** MIT license; STT list includes Whisper, Parakeet (v3 25 European languages; streaming via `stream=True`), Voxtral, Voxtral Realtime (4B, adjustable delay), Nemotron 3.5 streaming (40 locales); no Indic STT listed; quantization 3/4/6/8-bit and mxfp/nvfp modes — [mlx-audio README](https://github.com/Blaizzy/mlx-audio)
- **CoreML IndicConformer:** `phequals/indic-conformer-600m-multilingual-coreml-rnnt` — INT8 encoder with fixed 1024-frame input (long audio must be windowed and stitched), RNNT greedy with blank id 256 / start token 5632 / max 10 symbols per frame; 7 language heads (hi, bn, mr, te, ta, ml, kn); caller must pick the language; `.mlmodelc` must be regenerated on-device; no RTF/WER; MIT tag — [phequals CoreML card](https://huggingface.co/phequals/indic-conformer-600m-multilingual-coreml-rnnt)
- **whisper.cpp streaming:** `examples/stream` is described as "naive"; default mode transcribes a rolling window about every 0.5 s; `--step 0` uses a "very basic" energy VAD then transcribes the last `--length` ms; output hard to pipe (ANSI rewriting) — [whisper.cpp stream example](https://github.com/ggml-org/whisper.cpp/tree/master/examples/stream)
- **faster-whisper (CTranslate2):** project benchmark: small model int8 CPU (i7-12700K, 8 threads), 13-min file in ~1m42s (RTF ~0.13) offline, beam 5; batched ~51 s — [faster-whisper on PyPI](https://pypi.org/project/faster-whisper/) (figure relayed via search summary; offline, desktop CPU, not streaming)
- **Whisper on Hindi/Telugu:** un-fine-tuned Whisper-small normalized WER 211.7 on 93 Telugu samples (tiny set; fine-tune on 99 clips gets ~73); LoRA project reports FLEURS Hindi 46.3 and Telugu 100.1; Hindi baseline 0.515 WER on 30 FLEURS utterances — [Whisper-small-te card](https://huggingface.co/bhavik2026/whisper-small-te), [LoRA Hindi card](https://huggingface.co/manishehehe/whisper-small-hindi-lora) (small, noisy evals)
- **Moonshine:** library MIT; "models are MIT by default too, in every language and at every size", except legacy non-streaming non-English models under the non-commercial Moonshine Community License; runs on Python, JS/WASM, iOS, Android, macOS, Linux, Windows, Raspberry Pi; README mentions no Hindi/Telugu — [moonshine-ai/moonshine](https://github.com/moonshine-ai/moonshine)
- **Kyutai DSM/moshi:** `stt-1b-en_fr` (~1B, 0.5 s delay, semantic VAD, en+fr) and `stt-2.6b-en` (2.5 s delay, en only); weights CC-BY 4.0; Python code MIT, Rust backend Apache; MLX via `moshi-mlx` (`kyutai/stt-2.6b-en-mlx`), 1B tested on iPhone 16 Pro; Rust server examples are CUDA (L40S batch 64 ~3x real time; H100 400 streams); CPU-only performance not documented — [Kyutai DSM repo](https://github.com/kyutai-labs/delayed-streams-modeling), [stt-1b-en_fr card](https://huggingface.co/kyutai/stt-1b-en_fr)
- **NeMo's own export:** the NeMo cache-aware paper does not discuss ONNX export — [arXiv 2312.17279v3](https://arxiv.org/html/2312.17279v3). I found no official NeMo/Riva page documenting ONNX export of cache-aware models (search returned only a community HF discussion; see Key Question B). nemotron-3.5 card: runtime NeMo 26.06, HF Transformers >= 5.13.0 (`AutoModelForRNNT`), q8_0 GGUF for NeMo-Speech.cpp, no ONNX mention — [nemotron-3.5-asr-streaming-0.6b card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)

### Inferences
- True-streaming options on laptop CPU that cover Hindi today: Nemotron-3.5 via sherpa-onnx (ONNX), ORT-direct, OpenVINO, CrispASR/GGUF, CoreML/MLX. Whisper/whisper.cpp/faster-whisper are windowed re-decoding, not true streaming, and Telugu is unusable zero-shot.
- Kyutai 1B and Moonshine cannot be base models for Hindi/Telugu without a from-scratch/large retrain; their licensing is fine but language coverage and (for Kyutai) the 1B-param/CPU unknowns rule them out. I found no evidence that Kyutai's 1B model runs in real time on laptop CPU (only iPhone 16 Pro via MLX/Swift, which implies Apple-silicon feasibility but no RTF).

### Gaps
- No RTF for CoreML/MLX/OpenVINO Nemotron on laptops; no official CTranslate2/whisper.cpp/onnxruntime licenses fetched (MIT for these is background knowledge, not verified here); no NeMo `export_cache_support` official doc; Moonshine model/latency page 404'd.

## 3. Quantization: ORT int8, per-channel, WER impact, fp16/bf16 on Apple, QAT, layers to keep fp32, sizes

### Takeaway
Weight-only block quantization (ORT MatMulNBits) on the encoder is the best-documented path: int8 is lossless (8.03 -> 8.01 WER) and even int4-mixed costs only ~0.1 abs; the integer-arithmetic path (ConvInteger/MatMulInteger) is what hurts (8.20 -> 10.14). Keep decoder LSTM, joiner, cache tensors and (in GGUF) pre-encode conv in fp32. sherpa-onnx's default int8 assets exist for all Nemotron chunk sizes but there is no published int8-vs-fp32 WER for them.

### Cited Findings
- Microsoft ORT study of Nemotron-0.6B (8-dataset avg WER, streaming config (7,10,7) = 0.56 s delay): PyTorch CUDA 7.28; ONNX FP32 8.03; int8 k-quant 8.01; int4-mixed (Q/K/V/O in all layers + first/last encoder layer kept int8) 8.12; int4 k-quant 8.20; int4 RTN 8.46; int4 k-quant + ConvInteger/MatMulInteger 10.14. Sizes: PyTorch/ONNX FP32 2.47 GB; int8 k-quant 1.28 GB; int4-mixed 0.73 GB; int4 0.67 GB. Weight-only, block size 32, MatMulNBits, activations FP32; decoder (LSTM) + joiner kept FP32 (<35 MB combined); cache tensors FP32; only encoder quantized — [arXiv 2604.14493 (HTML)](https://arxiv.org/html/2604.14493)
- Same paper: CPU AMD EPYC 7V12 (AVX2, 2.45 GHz) pinned to 32 cores, batch 1: RTFx FP32 6.73, int8 7.25, int4 variants 7.15-7.30, int4+ConvInteger 8.00; at 0.16 s delay (2,20,2) int4 gives WER 8.89 and RTFx 2.87; reducing left context from 10 to 2 chunks (5.6 s -> shorter) raises WER 7.28 -> 8.51. Quantization gives modest speedups (~8% for int8) because it is memory/weight bound — [arXiv 2604.14493](https://arxiv.org/html/2604.14493); abstract: size 2.47 GB -> 0.67 GB with WER within 1% abs of PyTorch — [arXiv abs](https://arxiv.org/abs/2604.14493)
- ORT docs: dynamic quantization recommended for RNN/transformers, static for CNNs; per-channel can help when weight ranges are large and on AVX2/AVX512 non-VNNI generally needs `reduce_range` (7-bit weights); U8S8 on x86 "might suffer from saturation" (try reduce_range or U8U8); S8S8+QDQ is the default first choice, S8S8+QOperator slow on x86-64; x64 with VNNI and Arm have no saturation issue — [ORT quantization docs](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
- ConvInteger pitfall: upstream IndicConformer `model.int8.onnx` fails to create an ORT CPU session ("Could not find an implementation for ConvInteger(10)") because the CPU ConvInteger kernel supports only uint8; fix = re-quantize QInt8 -> QUInt8; per-language Hindi/Telugu/etc. packs shrink to 131 MB each (vs 622 MB for the 22-language model); external-data weights cut resident initializer memory 202 MiB -> ~30 MiB on iPhone; 80.3% exact-word match on 61 words (tiny eval) vs 86.9% for the 22-language model — [nmukthap/vertexvoice-indic](https://huggingface.co/nmukthap/vertexvoice-indic)
- Streaming Conformer-Transducer int8: WER 8.19 -> 8.40 (~2x speedup), attributed to softmax staying float — [arXiv 2010.11395](https://arxiv.org/pdf/2010.11395); Q-ASR (integer-only zero-shot) <1% degradation on Conformer — [arXiv 2103.16827](https://arxiv.org/abs/2103.16827v3) (via search summaries)
- 2026 TTS study: ORT dynamic INT8 with per-tensor activation scales raised WER 0.028 -> 1.11; restricting int8 to MatMul kept quality while convolutions were the culprit — [arXiv 2609.28974](https://arxiv.org/pdf/2609.28974) (TTS, not ASR; search summary only)
- sherpa-onnx streaming Zipformer 66M (Indian English fine-tune): int8 total ~68 MB (encoder 67 MB) vs fp32 ~252 MB (encoder 249 MB); Svarah WER 27.96 (int8 greedy) vs 26.90 (fp32 modified beam search; confounded by decoding method) — [Akshatkasera007 zipformer card](https://huggingface.co/Akshatkasera007/STT-streaming-zipformer-indian-en)
- sherpa-onnx int8 export of Nemotron-speech-streaming-en-0.6b @1120 ms = 464 MB on disk; OpenWhispr reports ~632 MB (EN) and ~650 MB (3.5 multilingual) INT8 ONNX — [Softcery](https://softcery.com/lab/hosting-nemotron-asr-streaming-on-a-cpu.md) vs [OpenWhispr](https://openwhispr.com/blog/local-streaming-speech-to-text) (conflict; packaging differences likely, not confirmed)
- GGUF: Q4_K 458 MB vs F16 1.29 GB, identical output on one JFK clip, no WER table — [cstr GGUF card](https://huggingface.co/cstr/nemotron-3.5-asr-streaming-GGUF). MLX quant loss: 5-bit 11.53 vs 8-bit 11.01 avg WER (6 FLEURS langs) — [soniqo](https://soniqo.audio/guides/nemotron)
- Hindi 120M IndicConformer ONNX (OpenVoiceOS) ships fp32 + int8 weights, MIT, no sizes/WER — [OpenVoiceOS hi-onnx](https://huggingface.co/OpenVoiceOS/ai4bharat-indicconformer-hi-onnx)

### Inferences
- Disk sizes (estimates, not measured by me): 120M-param conformer int8 ~ 120-150 MB (the 131 MB Hindi/Telugu per-language IndicConformer pack, which includes joint + vocab, is the closest measured analogue); 600M int8 ~ 460-650 MB with sherpa dynamic int8 or ~1.3 GB with ORT weight-only int8 k-quant (the MS int8 file is larger since it keeps scales/fp32 parts); int4 ~ 0.67-0.73 GB.
- Priority order for post-trained model: (1) weight-only int8 on encoder MatMuls (no accuracy loss expected), (2) dynamic int8 as in sherpa assets, validate on Indic dev set, (3) avoid ConvInteger/activation-quantized convs, keep conv module and pre-encode (subsampling convs) in fp32 or weight-only, (4) keep joiner/decoder fp32 (tiny). No QAT evidence for ASR on this stack found in this session.
- On Apple silicon, use MLX 8-bit/bf16 or CoreML INT8 rather than ORT int8 (ORT dynamic quant docs have no Apple-specific guidance); 5-bit costs ~0.5 abs WER on multilingual FLEURS.

### Gaps
- No published int8-vs-fp32 WER on Hindi/Telugu for any streaming conformer; no QAT results for FastConformer; fp16/bf16 behavior on ORT CoreML EP not covered; per-layer LayerNorm/positional-attention sensitivity not found (MS paper says Q/K/V/O projections and first/last encoder layers are the sensitive ones at int4).

## 4. Realistic latency / RTF / memory numbers on CPU

### Takeaway
Best measured data: sherpa-onnx 1.13.8 + ORT 1.28.2, int8 Nemotron-0.6B, 1120 ms chunk, Ryzen 7500F (6C, AVX512) gives ~0.063 s CPU wall per audio second on 4 threads (RTF ~0.06) in-process with ~45-75 ms finalization, ~1.0 GB RAM; shrinking chunk to 80 ms raises processing cost 10x (RTF 0.65). No measured i5/i7 12th-13th gen or M1-M3 numbers for a streaming FastConformer were found; M2 data is limited to core-seconds.

### Cited Findings
- Softcery (Sept 2026), Ryzen 7500F 6C/32 GB container, no GPU; Mac M2 for cost sampling; sherpa-onnx 1.13.8, ORT 1.28.2; model = int8 export of nemotron-speech-streaming-en-0.6b, 1120 ms, 464 MB; greedy search; 0.5 s preroll:
  - Memory: 33 MB before load; 977-1,136 MB after load; ~+100 MB per 4 concurrent streams; Mac 2-4 threads ~1.0-1.14 GB
  - Processing per audio second, 4 threads in process (16.7 s clip): EN 1120 ms = 63.0 ms; 3.5-multilingual 1120/560/320/160/80 ms = 61.3/96.7/145.4/274.6/645.6 ms; finalization 75/74/59/47/45/45 ms (floor ~45 ms); test-clip WER 6.93 (EN), 7.91/7.99/8.27/8.88/9.43 for 3.5 at 1120...80 ms
  - Socket, 6 threads: 1120 ms chunk final p50 66 ms/p90 212 ms, RTF/stream 0.327 at 12 callers; 560 ms chunk final p50 54 ms but RTF 0.478; first partial p50 1.62 s (1120 ms chunk)
  - Single-stream RTF "per stream, unpaced" at 1 caller 4 threads = 0.085; 12 callers 0.346; 24 callers 0.680; 48 callers 1.293 (breaks between 24 and 48); thread sweep at 12 callers: 1/2/3/4/6/8/12 threads RTF 0.321/0.333/0.342/0.354/0.391/0.480/0.564 (oversubscription beyond 6 cores hurts); `session.intra_op.spin_duration_us=200` cut 6-thread RTF ~25%

- A 600M streaming FastConformer int8 on a 6-8 core AVX2/AVX512 laptop should run at RTF ~0.06-0.15 at 1120/560 ms chunks and single stream (estimate from the Ryzen/EPYC numbers, not measured on i5/i7-12/13th gen). A ~120M model should be roughly 4-5x cheaper per audio second (parameter-count scaling; not measured).
- User-perceived latency = chunk size + finalization (~45-75 ms) + VAD/endpoint delay; algorithmic latency for chunk C is ~C/2 average (per NVIDIA paper, "average latency is about half the look-ahead"). 160-320 ms chunks are the practical Pareto point (RTF 0.14-0.27 on 4 threads Ryzen, WER +0.6-1.5 vs 1.12 s).
- M-series: Mac M2 2-thread sample suggests wall RTF <= ~0.09 if both threads were saturated (derived from 0.176 core-s/audio-s; inference only).

## 5. Streaming application layer: VAD, endpointing, chunking, P&C, ITN, hotwords, timestamps, partial stability, language ID

### Takeaway
Silero VAD (MIT, verified from LICENSE) is the safe VAD; TEN VAD is faster/smaller but carries "Apache 2.0 with additional conditions". Real-world pitfalls for cache-aware streaming are about flushing (trailing silence chunk), pre-roll and never cutting a stream mid-utterance. Hindi P&C: Nemotron-3.5 emits native punctuation/capitalization; separate P&C models for Indic are thin (Cadence-Fast, indic-punct). Hindi ITN exists in NeMo-text-processing; Telugu ITN not found.

### Cited Findings
- Silero VAD license file: MIT, Copyright Silero Team 2020-present — [LICENSE](https://raw.githubusercontent.com/snakers4/silero-vad/master/LICENSE); search results showed a "CC BY-NC 4.0" badge in the README that I could not reconcile — [search summary](https://pypi.org/project/silero-vad). NVIDIA's packaged Silero is under the RIVA license instead — [NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/teams/riva/models/silero_vad?version=v5)
- TEN VAD: "Apache 2.0, with additional conditions"; the root TEN-framework LICENSE (a different repo) forbids hosting on end-user devices/mobile and competing with Agora — I did not confirm the ten-vad repo carries the same conditions. Reported RTF 0.0086-0.016 (Ryzen 9 5900X 0.0150; i7-10710U 0.0150; Apple M1 0.0160; Xeon Gold 6348 0.0086 vs Silero 0.0127); library 306 KB (Linux) vs Silero 2.16-2.22 MB; sherpa-onnx integrates both (ten-vad since 1.12.6) — [TEN VAD repo](https://github.com/TEN-framework/ten-vad), [TEN-framework LICENSE](https://raw.githubusercontent.com/TEN-framework/ten-framework/main/LICENSE) (surfaced in search)
- Cache-aware streaming practicalities (sherpa-onnx online server, Nemotron): without one chunk of trailing silence the last partial chunk never reaches the encoder and final loses its last words; VAD reports speech late so feed 0.5 s preroll; only cut streams at utterance ends (mid-utterance cut loses left context); skip/resample non-16k audio; unknown session option keys silently dropped; batched decode over streams by one thread lost at every concurrency; endpoint detection was disabled and VAD-driven turn handling used — [Softcery](https://softcery.com/lab/hosting-nemotron-asr-streaming-on-a-cpu.md)
- OpenWhispr: partials must be replaced (not appended) because hypotheses revise; truncation-aware stop flush, fallback to re-decode full recording; sidecar process isolation — [OpenWhispr](https://openwhispr.com/blog/local-streaming-speech-to-text)
- sherpa-onnx lists punctuation (online/offline API in C++, Flutter, Go, Rust, HarmonyOS) and removes spaces before punctuation in ASR results (1.13.4) — [changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog); I did not find an Indic punctuation model in sherpa's list
- Nemotron-3.5: native punctuation and capitalization (labels via Qwen3-32B) — [nvidia card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b); IndicConformer vocabularies mostly lack punctuation, so P&C is downstream — [phequals CoreML card](https://huggingface.co/phequals/indic-conformer-600m-multilingual-coreml-rnnt)
- Cadence-Fast (270M, Gemma-3-270M made bidirectional, distilled from Cadence): English + 22 Indian languages incl. Hindi, Telugu, predicts danda; MIT per a Replicate mirror (unconfirmed on HF), Gemma base terms apply; no ONNX export found — [Cadence paper arXiv 2506.03793](https://arxiv.org/pdf/2506.03793), [Replicate cadence-fast](https://replicate.com/onesoltech/cadence-fast). indic-punct (IndicBERT, 11 Indic languages incl. Hindi/Telugu; 2022; license not confirmed) — [paper listing](https://paperswithcode.com/paper/indic-punct-an-automatic-punctuation). punctuate-all / FullStop XLM-R models are MIT but European-only — [promptlayer punctuate-all](https://www.promptlayer.com/models/punctuate-all)
- ITN: NeMo-text-processing is a standalone repo; docs language matrix includes Hindi (hi) for TN/ITN (table text messy); grammars use Pynini/OpenFst (`pynini==2.1.5`); Apache-2.0 per third-party index, Pynini license not verified — [NVIDIA docs 25.09](https://docs.nvidia.com/nemo-framework/user-guide/25.09/nemotoolkit/nlp/text_normalization/wfst/wfst_text_normalization.html), [ClickPy](https://clickpy.clickhouse.com/dashboard/nemo-text-processing)
- Hotwords: see section 1 (transducer + modified_beam_search only) — [sherpa hotwords docs](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)
- Language ID: Nemotron-3.5 uses a 128-dim one-hot language prompt concatenated to encoder output; `target_lang=auto` emits a language tag per utterance; no explicit statement on intra-utterance code-switching; Telugu not among its 40 locales (Hindi is "transcription-ready"; Thai/Hebrew etc. "adaptation-ready"); Hindi WER penalty for auto-detect vs given LangID +1.4 to +3.3 abs depending on chunk — [nvidia card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b)
- Timestamps/ys_probs/ys_log_probs: sherpa-onnx 1.13.7 populates `ys_probs` in online NeMo transducer greedy decoders; 1.12.10 added TDT duration to APIs — [changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog)
- Cache-aware training details that matter for post-training: causal convs, LayerNorm instead of BatchNorm, no utterance-level feature normalization, hybrid loss alpha_ctc=0.3, multi-latency training improves all latencies (RNNT 6.2/5.5/5.2 vs 6.4/5.9/5.4 single-latency at 40/240/520 ms) — [arXiv 2312.17279v3](https://arxiv.org/html/2312.17279v3)

### Inferences
- Language ID for code-switch: if you post-train with a language prompt, prefer a single "hi-en"/"te-en" mixed prompt (or unconditioned multilingual head with one shared SentencePiece vocab) rather than per-utterance LID; the Hindi auto-detect penalty in Nemotron (up to +3.3 abs) shows per-utterance LID hurts and doesn't model intra-utterance switching. A separate LID model is unnecessary if the vocab covers Devanagari + Telugu + Latin.
- Rule-based endpointing should be backed by a Silero VAD gate with >=0.5 s pre-roll and a final "flush" chunk; EOU-model options were not found in sources.
- TEN VAD license must be reviewed by counsel before shipping on end-user devices; Silero is the lower-risk default.

### Gaps
- sherpa-onnx rule-based endpoint doc (404); EOU (end-of-utterance) model sources not found; Telugu ITN not found; no small Indic P&C model with a verified permissive license + ONNX; partial-stability metrics (unstable-word rate) not found in sources.

## 6. Romanization / transliteration as an optional deterministic layer

### Takeaway
No off-the-shelf tool does phonetically natural Hindi romanization plus English-loanword handling deterministically and permissively. Best design: deterministic scheme-based transliteration (MIT-licensed `indic_transliteration` or own tables) + a small schwa-deletion step for Hindi + a lexicon for English loanwords in Devanagari/Telugu script; IndicXlit (MIT) only as an optional non-deterministic neural fallback. Aksharamukha is GPL-3 (avoid shipping in a closed binary).

### Cited Findings
- IndicXlit (AI4Bharat): code and models MIT; older Xlit models CC BY-SA 4.0; datasets CC BY 4.0 — [AI4Bharat page](https://ai4bharat.iitm.ac.in/?p=1121), [PyPI ai4bharat-transliteration](https://pypi.org/project/ai4bharat-transliteration/), [IndicNLP-Transliteration repo](https://github.com/AI4Bharat/IndicNLP-Transliteration)
- `indic_transliteration` (sanskrit-coders): MIT; supports ITRANS, Harvard-Kyoto, Velthuis, IAST, SLP1, OPTITRANS; Telugu as target script; Devanagari source/target; README mentions no ISO 15919/Hunterian and no schwa deletion — [indic_transliteration](https://github.com/sanskrit-coders/indic_transliteration)
- Aksharamukha: repo includes `gpl-3.0.txt` (GPL-3.0 inferred; aggregator says GPL-3.0, separate CLI AGPL-3.0); lists ITRANS and "ISO" schemes; supports Telugu; no mention of Hindi schwa handling — [aksharamukha-python](https://github.com/virtualvinodh/aksharamukha-python)
- uroman: Rust port Apache-2.0; PyPI says Apache-2.0; a mirrored original LICENSE.txt (2015-2020 Ulf Hermjakob, USC ISI) reads like MIT — unresolved, check isi-nlp/uroman repo — [docs.rs uroman](https://docs.rs/crate/uroman/0.6.7), [mirror LICENSE](https://huggingface.co/spaces/Afrinetwork/sts1/blob/bc747e61c9c717c85078eaef6ffcfd3bbe93e9c2/uroman/LICENSE.txt)
- Dakshina (Google): Latin-script romanization data for 12 South Asian languages (Hindi, Telugu included), built from Wikipedia; catalog lists CC BY-SA 4.0 (unconfirmed against repo) — [arXiv 2007.01176](https://arxiv.org/pdf/2007.01176), [awesome.ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fgoogle-research-datasets%2Fdakshina)
- Schwa deletion: unsolved by plain mappings; Arora et al. (ACL 2020) orthography-only classifier trained on pronunciation lexicon beats prior approaches; rule-based Choudhury (2004) six rules (e.g. word-initial schwa never deleted; schwa before full vowel kept) combined with stress analysis in a 2012 transliteration paper — [ACL 2020.acl-main.696](https://aclanthology.org/2020.acl-main.696), [C12-3014](https://aclweb.org/anthology/C12-3014.pdf)
- Standards: Hunterian maps अ to plain "a" without deletion marking; UNGEGN says always romanize the inherent vowel except name-final, and notes no evidence of use in India/cartography; ISO 15919 is a diacritic-rich multi-Brahmic standard (deletion procedure not described in sources found) — [Hunterian (Wikipedia)](https://en.wikipedia.org/wiki/Hunterian_transliteration), [UN Hindi report](https://unstats.un.org/unsd/ungegn/working_groups/wg5/documents/wgrr4hindi.pdf), [Wikipedia schwa deletion](https://en.wikipedia.org/wiki/Schwa_deletion_in_Indo-Aryan_languages)
- Loanword spelling in Hindi is inconsistent (e.g. डॉलर vs डालर); no standard reference for back-transliteration of English loanwords to Latin found; rule-based back-transliteration literature is mainly Sanskrit (HK -> Devanagari) — [Amrita paper](https://www.amrita.edu/publication/a-roman-to-devanagari-back-transliteration-algorithm-based-on-harvard-kyoto-convention/), [Wikipedia Hindustani orthography](https://en.wikipedia.org/wiki/Hindustani_orthography)

### Inferences (design proposal; labelled as my recommendation, not sourced)
- Layered, deterministic romanization: (1) tokenise ASR output by script; Latin tokens pass through unchanged; (2) lexicon lookup for Devanagari/Telugu-script English loanwords (reverse of an English-word->Devanagari list, e.g. mined from your own training transcripts where code-switched words are known) emitting the English spelling; (3) otherwise scheme transliteration (ISO 15919 or a simplified "Hunterian-like" table) with a Hindi schwa-deletion pass (Choudhury-style rules for default, optional Arora classifier if allowed); Telugu keeps inherent vowels explicit (no schwa deletion needed; background linguistics, not in my sources); (4) fully versioned tables so output is reproducible; reversibility only guaranteed for the strict scheme (ISO 15919) and not for the "natural" mode.
- Two output modes: "scholarly" (ISO 15919, reversible) and "natural/chat" (Hunterian-like, schwa-deleted, loanwords restored).
- Evaluation: (a) round-trip CER for strict scheme; (b) Dakshina romanization test sets for "natural" agreement (token-level exact match + CER against attested romanizations; note multi-reference nature and CC BY-SA data licensing for evaluation use); (c) loanword recovery rate on a code-switched held-out set; (d) schwa-deletion accuracy vs a lexicon; (e) human preference on a small panel. Avoid IndicXlit in the deterministic path (stochastic beam, model dependence) but it's a reasonable comparison baseline.

### Gaps
- ICU/CLDR transliterators (Devanagari-Latin, Telugu-Latin): no source retrieved (ICU's Unicode license being permissive is background knowledge, unverified); ISO 15919 official machine rules and Hunterian formal tables for Telugu not retrieved; uroman and Dakshina licenses need repo-level confirmation; no existing English-loanword back-transliteration lexicon with known license identified.

## 7. Packaging, benchmark harness, CI, signing/versioning

### Takeaway
There is no standard on-device ASR benchmark/CI kit in my sources; the best templates are Softcery's methodology and the Microsoft paper's metrics. Signing/versioning guidance was not found in sources and is purely my proposal.

### Cited Findings
- Softcery benchmark hygiene: report RTF as processing time / audio time (unpaced) and at speech speed (paced); p50/p90 final-transcript latency; thread sweeps vs cores; concurrency sweep to the breaking point; memory before/after load and per added stream; run-to-run noise (~2.5 ms at 1 caller, ~16.5 ms at 12); a gate that refuses to run when 1-min load average > 1.0; fixed normaliser and note that different WER normalisers (whisper-normalizer vs case/punct only) are not comparable — [Softcery](https://softcery.com/lab/hosting-nemotron-asr-streaming-on-a-cpu.md)
- Microsoft: evaluate quantization on 8 datasets at the production streaming config; ONNX re-implementation lost ~0.75 abs WER vs PyTorch (8.03 vs 7.28) even at FP32, so regress the exporter itself, not only quantization — [arXiv 2604.14493](https://arxiv.org/html/2604.14493)
- Version coupling evidence: OpenWhispr found older sherpa-onnx silently decoded Nemotron poorly rather than failing, requiring re-pinned binaries on every platform; recommends sidecar process isolation and fallback path — [OpenWhispr](https://openwhispr.com/blog/local-streaming-speech-to-text)
- CoreML packaging: `.mlmodelc` not distributed, must be compiled on the target Mac; `preprocessor_constants.bin` required — [phequals](https://huggingface.co/phequals/indic-conformer-600m-multilingual-coreml-rnnt); featurizer assets (`mel_filters.json`, `hanning_window.json`) are omitted by upstream exports and must be shipped — [vertexvoice-indic](https://huggingface.co/nmukthap/vertexvoice-indic)
- Model licenses of relevant bases: Nemotron-3.5 OpenMDW-1.1 (commercial OK with attribution per GGUF card; NVIDIA card says ready for commercial use); Nemotron-speech-streaming-en under NVIDIA Open Model License; AI4Bharat IndicConformer MIT; Kyutai CC-BY 4.0 — [nemotron-3.5 card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b), [EN card](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b), [OpenVoiceOS hi-onnx](https://huggingface.co/OpenVoiceOS/ai4bharat-indicconformer-hi-onnx), [Kyutai](https://huggingface.co/kyutai/stt-1b-en_fr)

### Inferences (proposal)
- Harness: golden audio set (Hindi, Telugu, English, code-switched; clean and noisy) streamed paced at 1x and unpaced; log RTF, p50/p90 chunk and final latency, first-partial latency, peak RSS, partial-revision rate, WER/CER for fp32 vs int8 vs weight-only; fail CI if WER regresses > 0.3 abs, RTF > budget, or any numerical divergence beyond threshold between PyTorch cache-aware streaming simulation and ONNX streaming output on a fixed clip (catches export bugs like normalisation, cache tensor order).
- Packaging: single versioned model bundle (encoder/decoder/joiner/tokens/metadata + manifest with SHA-256, runtime version pin e.g. sherpa-onnx >= 1.13.5, tokenizer hash, chunk size, quantization recipe); sign with detached signature (e.g. Sigstore/cosign or minisign) and verify at load; semantic model versioning separate from runtime versioning.

### Gaps
- No sources on signing/versioning practice for on-device ASR bundles; no CI templates found.

## Key Question A: What is the lowest-risk stack that gets a post-trained streaming Indic model running on laptop CPU?

### Takeaway
Post-train a NeMo cache-aware FastConformer RNNT (hybrid CTC/RNNT) checkpoint (ideally starting from Nemotron-3.5-streaming-0.6B since it already has Hindi, 128-mel, prompt conditioning, OpenMDW license) and ship it through sherpa-onnx (encoder/decoder/joiner int8 ONNX), with Silero VAD and a small P&C/ITN layer; use MLX/CoreML only as an optional Apple-native path. If 600M is too heavy, the 120M IndicConformer lineage is offline-only and would need re-training cache-aware.

### Cited Findings
- (see sections 1-5 for evidence: sherpa-onnx Apache-2.0 with maintained NeMo streaming loaders; Nemotron-3.5 supports Hindi not Telugu; OpenMDW-1.1 license; sherpa int8 ONNX RTF ~0.06 at 1120 ms on 4 threads Ryzen)
- Telugu is not a supported Nemotron-3.5 locale and AI4Bharat Hindi/Telugu models are offline — [nvidia card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b), [IndicConformer hub](https://huggingface.co/ai4bharat/IndicConformer/tree/main)
- An existing streaming-on-offline-model approach for Indic (VEXYL-STT) uses energy VAD around AI4Bharat 600M, i.e. not cache-aware — [Medium VEXYL-STT](https://medium.com/@anilmathewm/vexyl-stt-free-self-hosted-indian-language-speech-to-text-server-f2909003aaf6)

### Inferences
- Recommended stack (my synthesis): Training: NeMo (pin version matching sherpa export script, "NeMo from git main" per sherpa README) -> post-train Nemotron-3.5 (or `stt_en_fastconformer_hybrid_large_streaming_multi` if you need a smaller/ older recipe) with extended SentencePiece vocab for Telugu + Hindi + English, multi-latency training. Export: sherpa-onnx's `export_onnx.py` pattern at chosen chunk (320 or 560 ms default; 160 ms optional), fp32 + int8; verify fp32 ONNX vs NeMo streaming simulation. Runtime: sherpa-onnx >= 1.13.5 pinned, ORT CPU EP, 4-6 threads, spin option, sidecar process. App layer: Silero VAD (MIT) with 0.5 s preroll, flush chunk, model P&C (train it in; Nemotron already emits it), NeMo-text-processing Hindi ITN or custom rules, optional romanization module. Apple: same ONNX on CPU as baseline; optional MLX 8-bit/CoreML path after validation (no RTF data available).
- Fallback plan if sherpa loader limits bite (e.g. language-prompt features, TDT streaming): ORT-direct three-session runtime following Microsoft's design, or Zipformer streaming transducer through icefall -> sherpa-onnx (most mature loader, 66M int8 = 68 MB, RTF 0.035 on Xeon 4 threads).

### Gaps
- No evidence on post-training Nemotron-3.5 with a new language (Telugu) via the prompt-dictionary mechanism; sherpa-onnx handling of a modified `prompt_dictionary`/vocab not documented.

## Key Question B: Which architectures have first-class streaming support in the runtime (so base-model choice should be constrained)?

### Takeaway
sherpa-onnx: streaming Zipformer transducer (most mature, many models), NeMo cache-aware FastConformer transducer (Nemotron EN/3.5) and NeMo online CTC, streaming Paraformer, LSTM and (zh) Conformer transducers. Not first-class: Whisper (offline only), wav2vec2, TDT-streaming, Moonshine/Kyutai. ORT-direct supports anything you wire up yourself.

### Cited Findings
- Streaming model families in sherpa-onnx: online transducer, online Paraformer, online CTC — [sherpa-onnx README](https://github.com/k2-fsa/sherpa-onnx); transducer list: Zipformer, Conformer, LSTM — [online-transducer index](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/index.html); NeMo streaming transducer/CTC support milestones — [changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog)
- NeMo Parakeet "Unified" is handled via a *buffered* RNNT streaming path (1.13.2) not cache-aware — [changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog)
- NeMo cache-aware FastConformer checkpoints: non-streaming Fast Conformer can use limited-context attention but "global tokens still require training" (NeMo 24.09 docs, via search) — [NeMo ASR models docs](https://docs.nvidia.com/nemo-framework/user-guide/24.09/nemotoolkit/asr/models.html)

### Inferences
- Constrain base-model choice to: NeMo cache-aware FastConformer RNNT/hybrid; icefall streaming Zipformer transducer. Prefer RNNT over CTC-only if you need hotwords/modified beam search.
- Offline-only bases (IndicConformer-600M, Whisper, wav2vec2) would have to be re-trained/fine-tuned with chunked/limited-context attention to be truly streaming; buffered re-decoding is a latency/compute compromise (paper: buffered RNNT 11.3% WER at 2 s vs cache-aware 6.3% at 1.36 s on LS test-other — [arXiv 2312.17279v3](https://arxiv.org/html/2312.17279v3)).

### Gaps
- Official sherpa-onnx statement of which NeMo streaming variants (80/480/1040 ms hybrid; Nemotron) are supported for CTC vs transducer heads.

## Key Question C: Specific export pitfalls for NeMo cache-aware FastConformer and for hybrid CTC/RNNT

### Takeaway
The known pitfalls: feature normalization must be "NA" (not per-feature) at export, you must enable cache support / use `forward_for_export` with the three cache I/O tensors, attention context ([left, right]) is baked into the exported graph (separate export per chunk size in sherpa), sherpa requires encoder/decoder/joiner split plus metadata, quantizing convs with ConvInteger can break or degrade, and runtime/exporter version drift silently degrades accuracy.

### Cited Findings
- Cache-aware encoder export (community recipe, quran FastConformer-hybrid CTC head): load `.nemo`, `eval()`, select CTC decoding, `encoder.set_default_att_context_size([left,right])` (author used [70,13]; [70,0] lowers latency, costs accuracy), enable `export_cache_support`, export through `encoder.forward_for_export`; inputs: mel (80 x T), length, `cache_last_channel`, `cache_last_time`, `cache_last_channel_len`; outputs: log-probs (1025 classes), encoded lengths, and three "next" caches fed back next chunk; set preprocessor normalization to "NA" in both the preprocessor object and config, otherwise the graph expects per-utterance normalization — [Muno459 discussion](https://huggingface.co/Muno459/fastconformer-quran-streaming/discussions/5). Author withheld the full script; sherpa not mentioned
- NVIDIA right-context values per model: Nemotron-EN `att_context_size` [70,{0,1,6,13}] = 80/160/560/1120 ms with 80 ms frames; Nemotron-3.5 uses [56,{0,1,3,6,13}] = 80/160/320/560/1120 ms; older hybrid NGC models [70,{0,1,6,13}] = 0/80/480/1040 ms and worst-case latency listed with average about half — [EN card](https://huggingface.co/nvidia/nemotron-speech-streaming-en-0.6b), [3.5 card](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b), [NGC hybrid large streaming multi](https://catalog.ngc.nvidia.com/orgs/nvidia/nemo/models/stt_en_fastconformer_hybrid_large_streaming_multi/-)
- Hybrid CTC/RNNT: shared encoder, loss = 0.3*CTC + RNNT, FastEmit 0.005 on RNNT; hybrid models beat non-hybrid at same latency — [arXiv 2312.17279v3](https://arxiv.org/html/2312.17279v3). In ONNX the transducer needs separate decoder/joiner sessions; NeMo emits combined decoder_joint, which must be split; FP32 decoder/joiner (<35 MB) — [pantinor mirror](https://huggingface.co/pantinor/ovos-conformer-mirrors), [arXiv 2604.14493](https://arxiv.org/html/2604.14493)
- Cache details: depthwise conv cache = K-1 steps per layer; MHSA cache grows up to left context then drops oldest; downsampling uses concatenated last mel frames instead of cache; paper has inconsistent 4x vs 8x subsampling statements; Nemotron uses 8x (80 ms frames) — [arXiv 2312.17279v3](https://arxiv.org/html/2312.17279v3), [GGUF card](https://huggingface.co/cstr/nemotron-3.5-asr-streaming-GGUF)
- Sherpa export for Nemotron-3.5: SentencePiece -> `tokens.txt`, metadata `prompt_dictionary`, `auto_prompt_id`, one export per chunk size — [sherpa export dir](https://github.com/k2-fsa/sherpa-onnx/tree/master/scripts/nemo/nemotron-3.5-asr-streaming-0.6b)
- Reduced left context lowers accuracy: (7,10,7) -> (7,2,7) WER 7.28 -> 8.51; ORT FP32 port itself 8.03 vs 7.28 PyTorch — [arXiv 2604.14493](https://arxiv.org/html/2604.14493)
- Quantization pitfalls: ConvInteger CPU kernel is uint8-only (QInt8 export fails to load); ConvInteger/MatMulInteger path degrades WER (10.14) — [vertexvoice-indic](https://huggingface.co/nmukthap/vertexvoice-indic), [arXiv 2604.14493](https://arxiv.org/html/2604.14493)
- Runtime coupling: older sherpa-onnx loaded Nemotron without error but decoded poorly; fix upgrade >= 1.13.4 (OpenWhispr); changelog shows "Fix greedy search decoding for NeMo streaming transducer" in 1.13.5 — [OpenWhispr](https://openwhispr.com/blog/local-streaming-speech-to-text), [changelog](https://pub.dev/packages/sherpa_onnx_linux/changelog)
- CoreML export constraint: fixed 1024-frame encoder input (non-streaming conversion) — [phequals](https://huggingface.co/phequals/indic-conformer-600m-multilingual-coreml-rnnt)
- Third-party mirror warning: NeMo checkpoints exported without sherpa metadata fail to load ("No model_type in the metadata!") — [pantinor mirror](https://huggingface.co/pantinor/ovos-conformer-mirrors)

### Inferences
- Checklist for the team: (1) export the same checkpoint at each target `att_context_size` and compare to NeMo's `conformer_stream_step` simulation on a fixed clip (cache tensor order/shape, logits parity <1e-3 fp32); (2) set normalize to NA and replicate NeMo mel front end exactly (128 mel for Nemotron, 80 for IndicConformer; 0.97 pre-emphasis, Slaney mel); (3) separate and verify decoder/joiner and write metadata expected by sherpa; (4) keep conv/pre-encode and decoder/joiner out of integer-activation quantization; (5) pin sherpa-onnx + ORT + NeMo versions together in the model manifest; (6) test the final-flush, preroll and left-context-reset behaviours in CI. Because the sherpa exporter writes fp32 and int8 per chunk, a hybrid CTC head is optional: export it only if you want a CTC fallback (sherpa has NeMo online CTC support since 1.12.8).
- The `[70,x]` vs `[56,x]` left-context differences between Nemotron EN and 3.5 mean a custom post-training run must fix and document the left context used at export, since it defines the cache tensor shapes.

### Gaps
- No official NeMo documentation of the cache-aware ONNX export procedure found (only community HF discussion); no sherpa-onnx doc enumerating cache tensor names it expects (inferred from NeMo's names); no public record of TDT cache-aware streaming export to sherpa-onnx.
