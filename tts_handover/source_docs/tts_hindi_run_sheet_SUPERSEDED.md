# Hindi TTS run sheet (under-a-week plan), 2026-10-14

**Status:** PROPOSED; nothing started. Part of `tts/pipeline.md` (REVISION v1.2). Log everything in `tts/progress.md`.
**Labels:** [M] read from a primary source; [E] our estimate; [P] our proposal; [U] unverified. Config names and settings below were read from Kyutai's repo on 2026-10-14 (`github.com/kyutai-labs/pocket-tts`, `training/`).

## 0. What we build
One **Hindi, single fixed-voice, ~110M-parameter, CPU-friendly TTS model**, by (1) **fine-tuning** Kyutai's released 24-layer English teacher (`pocket_tts/config/english_2026-04_24l.yaml`) on Hindi, then (2) **depth-distilling** it into the 6-layer student on one speaker's recordings.

**Why two stages (teacher, then student) and not train the small model directly?** Kyutai's README: "Training the model in two steps like this works better than training a 6-layer model from scratch" [M]. The 24-layer teacher (about 313M parameters [paper figure]) has the capacity to learn Hindi sounds and spelling from ~150 h; the 6-layer student (about 110M including the audio codec) then **learns to reproduce the teacher's internal activations**, copying the teacher's non-backbone weights and keeping the flow head frozen, and also bakes in classifier-free guidance (better quality without extra compute at run time) [M, `depth_distill.yaml`]. A community Korean run found the small model weaker when it was not done this way ("quite poor" student, usable teacher) [V]. Direct fine-tuning of the 6-layer model is not a documented recipe, so it could be a cheap side experiment but not the main plan; and the 24-layer teacher itself is a fallback to ship on laptops.

## 2. Tools and models
- **Base:** Kyutai Pocket TTS 24-layer English teacher; code MIT, weights CC BY 4.0 (gate accepted). Training needs **Linux + an NVIDIA GPU**; **~16 GB works at `batch_size: 16` with `grad_accum_steps: 4`** (default batch 64 wants ~54 GiB) [M].
- **Aligner:** `python -m training.scripts.align_data in.jsonl out.jsonl --model <HF char-level Wav2Vec2ForCTC> --device cuda`. It writes a `words` field (start/end per word). First choice **`Harveenchadha/hindi_large_wav2vec2`** (Apache-2.0 tag; Devanagari character vocabulary must cover our text); fallback **AI4Bharat IndicWav2Vec Hindi** (MIT). [M for the script, U for the models]
- **Tokenizer:** the repo's `train_tokenizer.py`, 4k SentencePiece on our transcripts, output `data/tokenizer.model`.
- **Judge (reads our audio back to count errors):** IndicConformer Hindi (needs AI4Bharat's NeMo fork) or, if that is slow to install, a Hindi Wav2Vec2-CTC model or Whisper large-v3.
- **Baselines for comparison:** Kyutai English Pocket TTS (speed), community Hindi model `saryps-labs/pocket-tts-hindi` (licence to be checked; baseline only).
- **Compute:** one AWS Linux GPU instance, `g5.2xlarge` (1x A10G 24 GB, 8 vCPU, 32 GiB, about $1.212/h on-demand per a price tracker) or `g5.xlarge`; 300 GB disk; **stop the instance as soon as a job ends.**

## 3. Steps
**Step 0. Today (owner).** (a) Accept the Rasa gate (`huggingface.co/datasets/ai4bharat/Rasa`); (b) submit the SYSPIN form; (c) approve spending (cap about $35) and tell me how to reach AWS; (d) say which voice policy applies (a fixed voice from an existing dataset speaker: see risk R4).

**Step 1. Setup (Day 1, ~$2).** Launch the instance; `git clone` the repo; `uv sync`; log in to Hugging Face on the instance **yourself** (`hf auth login`; I never handle the token); download SYSPIN Hindi (wget from the form's link) and Rasa Hindi (`huggingface-cli download ai4bharat/Rasa` with an include filter for Hindi). Rough raw size [E, arithmetic]: SYSPIN ~0.5 GB per hour, so ~50 GB; Rasa ~20 GB. Run the English Pocket TTS on CPU and time it; write the 100 test sentences.

**Step 2. Prepare the data (Day 2, mostly CPU).**
1. Inspect speakers and hours; **listen to 20 clips per voice** (also decides the student voice).
2. **Audio cleaning** (a Python script I write, run on CPU): (a) resample to **24 kHz mono** WAV (`ffmpeg -ar 24000 -ac 1`); (b) **trim silence at the two ends only** (never inside the sentence): cut leading and trailing audio quieter than about -40 dB relative to the clip's peak (energy threshold, e.g. `librosa.effects.trim` or ffmpeg `silenceremove`), then **keep ~0.25 s of padding** so no word is clipped and the model still learns a natural start and stop; thresholds are proposals tuned by listening to 50 clips; (c) normalise loudness (peak about -1 dB or ffmpeg `loudnorm`); (d) drop clips under 1 s or over 30 s (`max_duration_sec: 30.0` in the config), clips that clip (peak at full scale) and near-silent clips. Log how many clips each rule removes.
3. **Text cleaning** (a Python script I write): (a) Unicode **NFC**; remove zero-width and byte-order characters; (b) normalise punctuation: curly quotes to plain, collapse repeated spaces and repeated marks, remove symbols such as `# * _ ~` and emoji; **keep `, . ? ! ।`** (the danda ends Hindi sentences); (c) **numbers to words**: ASCII digits and Devanagari digits (०-९) become Hindi words (for example 2024 becomes "दो हज़ार चौबीस"); also `%` to "प्रतिशत", `₹500` to "पाँच सौ रुपये", dates and decimals by simple rules; library choice [U] (`num2words` Hindi support to be checked), otherwise a small converter we write and test on 100 examples; (d) common abbreviations and symbols (Dr., &, etc.) to Hindi words; (e) **English loanwords stay in Devanagari as in the data** (for example मीटिंग); clips whose transcript still contains Latin letters are set aside for inspection or dropped; (f) **character check:** keep only clips whose cleaned text uses characters the aligner's vocabulary knows (Devanagari letters, matras, nukta, virama, chandrabindu, anusvara, danda, space, basic punctuation); print every rejected line to review and count them; (g) remove exact duplicates and lines under 2 words; (h) **spot-check** 100 random cleaned lines by eye and 20 against their audio. Note for the app later: user text typed with Latin letters ("meeting") will not match this vocabulary, so the app needs a Latin-to-Devanagari step (for example a loanword lexicon or AI4Bharat IndicXlit, MIT) before synthesis.
4. Build `data/train.jsonl` and `data/valid.jsonl` with `{"path","duration","transcript"}` per line (validation split by speaker session).
5. **Align:** run `align_data` with the Hindi Wav2Vec2 model; spot-check 50 clips (cut points at word boundaries; no clipped first or last word); drop unalignable lines; output `data/train_aligned.jsonl`, `data/valid_aligned.jsonl`.
6. Train the **4k tokenizer** → `data/tokenizer.model`.
7. **Shards and a pilot (added 2026-10-15):** (a) **first run a pilot**: about 10 h from one archive, cleaned, aligned, tokenized, a few hundred training steps and a few generated sentences, to find alignment, tokenizer or config problems before processing everything; (b) then process **one archive at a time in shards of about 5,000 clips**; after each shard is cleaned and aligned, upload it to S3 and write a "done" marker so a crash resumes at the next shard; (c) merge the shards into one `train_aligned.jsonl` (and the one-voice student manifest); (d) **train on all the data mixed**, never chunk by chunk, to avoid forgetting earlier chunks. Rough scale [E]: 139 h is about 62,000 clips (SYSPIN ~9.3 s per clip, Rasa ~6.4 s), and 30k steps at an effective batch of 64 is about 1.9 million clips, so each clip is seen about 30 times.

**Step 3. Teacher fine-tune (Day 3).** Copy `training/configs/finetune_language.yaml` to `hindi_teacher.yaml` and set: `flow_lm.lookup_table.tokenizer_path: data/tokenizer.model`; `train_jsonl`/`valid_jsonl` to our aligned files; `run_dir: runs/hindi_teacher`; **`batch_size: 16`, `grad_accum_steps: 4`**; keep **`lr: 2e-4`** (constant, 1000 warmup; Kyutai: "keep lr at 2e-4: the text embedding starts random so the backbone has to move"), `start_from_pretrained: true`, `reset_text_embedding: true`; `max_steps: 30000` (Kyutai: "WER plateaus by ~15k; the rest is acoustic quality"; Prasad used 15k). Checkpoints and a sample wav every 2,500 steps. Run `uv run training/train.py training/configs/hindi_teacher.yaml` inside `tmux`. First run precomputes Mimi latents (~6 GB per 1,000 h). **Time:** 1x H100 does 6.3 steps/s at batch 64, so 30k steps is ~80 min there; on an A10G expect roughly 5-8x slower, about 7-11 h [E, unmeasured]. At each checkpoint listen to the sample and score 20 sentences with the judge; stop when error stops falling.

**Step 4. Student distillation (Day 4).** Copy `depth_distill.yaml` to `hindi_student.yaml`: `distill_teacher_weights` = our best teacher checkpoint; point the tokenizer to `data/tokenizer.model` in the student and teacher overrides [U: Prasad did this, the exact keys must be confirmed in the spike]; train on the **one-voice manifest (~50 h)**; keep `lr: 4e-4` cosine, `distill_cfg_coef: 2.0`; **`batch_size: 16`, `grad_accum_steps: 4`**; **`max_steps: 40000`** (Prasad's setting; Kyutai notes WER reaches parity by ~50k and similarity/UTMOS keep improving to ~150k). The config's `ema_decay: 0.9999` may lag in a 40k-step run, so compare the raw and EMA weights by ear [E]. **Time:** H100 10.5 steps/s (40k ≈ 1 h); A10G guess 5-8 h [E].

**Step 5. Evaluate (Day 5).**
- Generate the 100 test sentences, **one sentence at a time** (split on `।`, `.`, `?`, `!`), with `uv run pocket-tts generate --config <our yaml> --checkpoint <ckpt> --voice <prompt.wav> --text "..."`; sweep `--eos-threshold` once on a pinned checkpoint (Kyutai: too lax adds extra words, too strict cuts sentences).
- **Judge:** read-back CER; compare with the judge's CER on **real held-out speech from the same speaker**.
- **Listening test:** 8-10 colleagues, 20 sentences, naturalness 1-5, and A/B against the community Hindi model.
- **Speed:** int8 (`--quantize`) real-time factor, first-audio delay and RAM on your laptop; optional ONNX export (`KevinAHM/pocket-tts-onnx-export`) and Kyutai's `scripts/evaluate_quantization.py`.
- **Proposed pass marks [P]:** judge CER within 1.2x of real speech; mean listening score >= 3.5/5; >= 95% of sentences with no skipped or repeated words; >= 90% of numbers and dates read correctly; >= 3x real time on the laptop CPU in int8; first audio <= 300 ms.

**Step 6. Package and report (Day 6).** Weights (`.safetensors`), tokenizer (`.model`) and a config `.yaml` as in Kyutai's distribution notes; a notices file crediting Kyutai (CC BY 4.0 weights, MIT code), IISc SYSPIN (CC-BY-4.0) and AI4Bharat Rasa (CC-BY-4.0); a voice-rights note; a short report with audio samples and the numbers. If time remains, start **Telugu** with SYSPIN Telugu + Rasa Telugu (52.26 h), aligner IndicWav2Vec Telugu or `anuragshas/wav2vec2-large-xlsr-53-telugu`, judge IndicConformer Telugu.

## 4b. Compute, memory and storage sizing (added 2026-10-15)
- **GPU memory [M, Kyutai README]:** teacher fine-tune ~16 GB works at `batch_size: 16` with `grad_accum_steps: 4` (default batch 64 needs ~54 GiB on an H100); distillation ~9.8 GiB at batch 64. **One A10G (24 GB) is enough.** An A100 is not needed (on AWS it only comes as an 8-GPU p4d at about $21.96/h).
- **Recommended notebook [P]:** SageMaker `ml.g5.2xlarge` (1x A10G 24 GB, 8 vCPU, 32 GiB RAM). 4 vCPU and 16 GiB RAM would be tight for audio processing and data loading [E]. SageMaker notebook prices are above the plain EC2 price of $1.212/h [U]; check the SageMaker pricing page. Time: ~18-29 GPU-hours for Hindi [E].
- **Notebook volume [E]:** set **400 GB** (Hindi alone needs ~150 GB): extracted SYSPIN ~91 GB, Rasa ~20 GB, largest archive in flight ~24 GB, 24 kHz converted copies ~30 GB, Python env ~10 GB, checkpoints ~15-25 GB, samples/logs/latents a few GB. **Set `num_ckpt_keep` to 3 in `depth_distill.yaml` (default 999 fills the disk).**
- **S3 bucket [P]:** one private bucket in the same region as the notebook, block public access, encryption on, IAM role limited to the bucket. Prefixes: `raw/syspin/`, `raw/rasa/` (~110 GB backup, because the IISc links expire ~2026-10-21), `processed/hindi/` (24 kHz audio, manifests, tokenizer, ~15-20 GB), `checkpoints/` (best only, ~10-15 GB), `eval/`, `exports/`. About 150-200 GB, roughly $4-5 per month at ~$0.023 per GB-month [U]. Never store the signed download links or a Hugging Face token in the bucket or notebook files.
- **Notebook traps:** SageMaker notebook GPU types have their own service quota (often 0 by default; request "ml.g5.2xlarge for notebook instance usage" now); run long jobs in `tmux`; do not enable an idle-shutdown rule that could stop the instance mid-training (a terminal job looks idle), stop manually or end the job script with a stop command; storage is billed while the instance is stopped, so delete what is not needed at the end; the SYSPIN files are hosted in India, so `ap-south-1` may download fastest (g5 notebook availability there unconfirmed).
- **S3 vs notebook disk:** training code reads **local files**, so the working copy must be on the notebook volume; S3 is the durable backup and the hand-over between sessions. Pull only what is needed (the processed Hindi data, not the 91 GB raw) with `aws s3 sync`; same-region transfer between S3 and the notebook is free [U]. See TA-010.

## 5. Risks
- **R1 Speed:** nobody has measured Pocket TTS training on an A10G; the spike (Day 1-2) measures 200 steps and rewrites this sheet.
- **R2 Alignment:** the Hindi Wav2Vec2 model's character set must cover our transcripts; bad cuts clip words. Spot-check before training.
- **R3 Data:** the SYSPIN form may need approval and the download is large; SYSPIN quality must be checked by ear.
- **R4 Voice rights:** a shipped voice is a real speaker's voice from a CC-BY dataset; consent for a commercial synthetic voice is not documented; legal question TL-05; internal demo only until answered.
- **R5 Small model quality:** a Korean community run found the 100M student "quite poor" while the 24-layer teacher was usable; fallback is shipping the 24-layer teacher in int8 on laptops.
- **R6 Judge install:** AI4Bharat's NeMo fork may be slow to set up; fallbacks listed above.
- **R7 Numbers and English words** are weak spots for small models; test slice and number expansion.
