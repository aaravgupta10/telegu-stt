# Kyutai open-source speech releases: repo-level audit for a Hindi/Telugu/English edge STT (and possible TTS)

Date of check: **2026-10-12**. Method: read-only. GitHub REST API (unauthenticated), raw.githubusercontent.com, Hugging Face model/dataset API and raw model cards, arXiv HTML (2509.08753 DSM, 2509.06926 CALM). Nothing was downloaded beyond text/metadata; no clones, no weights, no logins.
Evidence labels as in `progress.md`: **[M]** read directly from a cited primary source today; **[V]** vendor/author claim; **[E]** my estimate; **[U]** unverified; **[C]** community (third-party) claim or measurement.

## 0. Bottom line (read this first)

| Senior's belief | Verdict | Evidence |
|---|---|---|
| (a) "Take the exact same thing (Kyutai), swap in Telugu data, PoC in an hour or two on 8 GPUs" | **TTS: partly true. STT: false.** | TTS: Kyutai released Pocket TTS **training code in Aug 2026** and a Telugu community model exists (124 h, 15k-step teacher fine-tune). STT: **no STT training or fine-tuning code exists in any Kyutai repo**; maintainers said on 2026-03-23 they will not release it; the only path is unofficial hacks on `moshi-finetune`, with no public Indic result. |
| (b) "An STT code release exists in the pocket-tts repo" | **False** [M] | `pocket-tts` full tree (14 releases, all branches) contains zero speech-to-text code. It is a TTS-only repo. STT inference code lives in `delayed-streams-modeling` (inference only) and `moshi` (Rust server). |
| (c) "Kyutai is versatile on many devices" | **True for Pocket TTS (CPU, ~100M). False for Kyutai STT** | STT is 1B/2.6B, officially GPU (CUDA Rust server) or Apple MLX. Community x86 laptop-CPU benchmarks of the 1B STT run at **3.0 to 8.4 frames/s vs the 12.5 frames/s needed for real time** (moshi.cpp alpha, Section 7). The claim "versatile on many devices" was not found verbatim anywhere; most likely it conflates Pocket TTS with the STT models. |

Recommendation (detail in Section 11): **do not build the STT on Kyutai.** Keep the NVIDIA FastConformer/Nemotron path for STT. Kyutai/Pocket TTS is a credible *separate* option only if TTS is in scope.

## 3. kyutai-labs/moshi-finetune: does it support the STT models?

[M] Apache-2.0; LoRA fine-tuning of **Moshi 7B speech-to-speech**, data = **stereo** wav + word-timestamped JSON (`annotate.py` uses Whisper); example config `example/moshi_7B.yaml`; README acknowledges code reused from `mistralai/mistral-finetune`. README never mentions STT/ASR/TTS. 16 open issues/PRs; relevant:
- **#4 comment by third party `jploski` (2025-07-16)** on DSM: "moshi-finetune already almost works for this task" for STT, **if you patch two files** (`train.py` to drop the audio loss; `moshi/models/lm.py` to skip the depformer when `dep_q == 0`), use **mono** wav, `ft_embed: true`, lr 2e-5, `duration_sec` 30. Reported peak 6.5 GB GPU, LoRA adapter ~421 MB, RTX 3090. Test was **3 files** teaching "Microsoft Word"; it overfitted [C]. Scripts at `github.com/jploski/moshi-finetune` [C].
- `eschmidbauer` (2025-10-15/16) trained an STT LoRA with that recipe and merged it; output on a Spanish-ish sample was a degenerate loop ("es lo que es lo que es lo que ...") ("maybe it overfit or dataset may not be quality") [C].
- `kikozi2000` (2025-08-19/22): fine-tuned Kyutai STT to a new language, **extended tokenizer 8k->16k**, short utterances fine, but streaming output **collapses to PAD after ~60 s (~750 frames)** and never recovers; no resolution posted [C].
- Maintainer `manukyutai` (moshi-finetune #9, 2025-07-07): "I would assume that if you want to change the language, ideally you want to retrain from scratch" (said about Moshi, untested); voice/domain changes: "lora fine tuning should be more than enough." `LaurentMazare` (#5/#7, April 2025): language adaptation of Moshi "likely to work if you have enough training data", cites J-Moshi; and (#7) "you can certainly try to adapt the loss so that it only considers the text stream ... The current code would have to be adapted to introduce the delay."
- **#21 (open, 2026-01-26):** someone building a **Hindi** Moshi (400 h stereo synthetic data) asks if massive mono pre-training is essential; cites J-Moshi's ~70k h pretraining vs 344 h stereo FT. **No answer; no reported Hindi result** [C, unresolved].

**Verdict:** moshi-finetune does **not officially support the STT models**. It can be hacked to; no evidence of a successful new-script STT fine-tune from this path.

## 4. kyutai-labs/pocket-tts: what is actually released

**Tree [M]** (v3.3.0, 2026-09-24; repo pushed 2026-10-11; created 2026-01-07): `pocket_tts/` (inference package: `models/{flow_lm,mimi,tts_model,text_chunking}.py`, `modules/`, `config/*.yaml`), `training/` (see below), `docs/`, `tests/`, `scripts/evaluate_quantization.py`, `scripts/generate_default_voices.py`, Docker/CI, `uv.lock`. 14 releases (v1.0.0 2026-01-13 ... v3.3.0 2026-09-24). 9 branches (`teacher-forcing`, `ci-training-tests-and-strict-zip`, ...). Discussions disabled.

**Any speech-to-text code? No [M].** Greps of the full file tree: no `stt`/`asr`/`whisper`/`transcribe` module. The only ASR-adjacent items are *evaluation/alignment helpers for TTS training*: `training/scripts/align_data.py` (CTC **forced alignment** with a HF `Wav2Vec2ForCTC`; docstring: "The default model is English; swap --model for another language (any char-level Wav2Vec2ForCTC works)"), and `training/eval/librispeech.py` (README: WER measured by transcribing generated audio with an external ASR, Granite ASR in the reference table; Whisper large-v3 suggested for other languages). The repo's issue search for "stt/asr/transcription" returns only TTS issues. **The senior's claim (b) is wrong.**

**Released inference models [M]** (README + `pocket_tts/config/`): English (`english`, `english_2026-01`, `-04`, `-09`, `-09_2`, `english_drifting_26-09`), plus French, German, Italian, Portuguese, Spanish, Dutch (the last added to the config folder; README lists "english, french, german, portuguese, italian, spanish, dutch"), each with a 6-layer default and a "_24l" higher-quality variant. **No Hindi, Telugu, or any Indic language is shipped by Kyutai.**
- Size: "100M parameters" (README); CALM paper App. F: "Pocket TTS has a size of 90M parameters while the VAE has 20M" (24-layer teacher: 313M, paper). Architecture: 6-layer flow-LM backbone (width 1024 per Hindi card) + 10M-parameter consistency/LSD head + Mimi VAE codec at 12.5 Hz, 24 kHz output.
- Speed [V, Kyutai README]: "~6x real-time on a CPU of MacBook Air M4", "Uses only 2 CPU cores", "~200ms to get the first audio chunk". On a 4-vCPU cloud x86 VM: RTF "~2.3-2.5x on CPU vs ~6.28x on GPU (Tesla T4)" [M, README "Running on GPU"]. int8 dynamic quantisation supported (CPU only).
- Voices: voice cloning from a wav prompt (the voice encoder is part of the released weights in `kyutai/pocket-tts`; the `-without-voice-cloning` repo omits it). 

**Training code (the `training/` directory, added "August 2026") [M]:**
- Files: `train.py`, `args.py`, `checkpointing.py`, `distributed.py`, `train_utils.py`, `dataloader/*`, `modules/{model,builders,conditioner,muon,samplers}.py`, `scripts/{prepare_data,align_data,precompute_latents,train_tokenizer,convert_tokenizer,shrink_checkpoint}.py`, `eval/{librispeech,release_checks}.py`, 5 configs (`scratch.yaml` 24L teacher, `depth_distill.yaml` 24L->6L student with CFG baked in, `finetune.yaml`, **`finetune_language.yaml`**, `drifting.yaml`), unit/smoke tests. The Mimi codec is **not** trained here (frozen; "Mimi is indeed trained independently", maintainer in pocket-tts#30).
- **Data format:** JSONL manifest `{"path","duration","transcript"}` -> after `align_data.py` adds `"words":[{"word","start","end"}]`. Training cuts each utterance at a random word boundary: audio before = voice prompt (<=5 s), audio after = target paired with the remaining words. Needs word-level alignment.
- **Hours guidance [M, training/README]:** "You can get something working with 100 hours of data, but for a strong model, you'll want 1000+ hours." "Use 200 hours of audio for a model that speaks, 2000 for one that actually sounds good." Prefer hand-transcribed over auto-transcribed. Latents: ~6 GB per 1000 h; ~60 GB disk per 1000 h.
- **Tokenizer:** SentencePiece **unigram, vocab 4000, character coverage 0.9995, byte fallback, digits split, normalisation off**, via `train_tokenizer.py`; `n_bins` must equal vocab size. **No phonemizer or G2P is required**; text goes in as native-script graphemes (that is how the community Hindi/Korean/Persian/Telugu models were built). Language-specific components you must supply: a **char-level `Wav2Vec2ForCTC` for the language** for forced alignment (e.g. Czech `comodoro/wav2vec2-xls-r-300m-cs-250`), and an ASR for WER evaluation. Caveat from the Telugu author (Section 8): **Meta MMS aligner is unusable for Telugu** (it romanises, no Telugu characters in vocab); and Pocket-TTS's internal sentence splitter finds boundaries via tokenizer pieces, which fails for Indic tokenizers -> split sentences yourself.
- **Fine-tune-from-English path (`finetune_language.yaml`)** [M]: starts from the released 24-layer English teacher, resets the text embedding (new tokenizer), keeps lr 2e-4 (README: lowering lr is slower; "the text embedding starts random, so the backbone has to move with it"). Kyutai's Czech result (PR #254, manu-lm, Kyutai collaborator): **976 h ParCzech**, from scratch 326% WER@2k steps, 45.7%@10k, 17.1%@15k, 16.2%@25k vs fine-tune 29.5%@2k, **12.0%@10k**, 11.3%@15k, 10.7%@25k (Whisper ASR judge; "swings of ~3 points between adjacent checkpoints are normal"); "WER plateaus by ~15k [steps]; the rest is acoustic quality"; README: fine-tune reached scratch WER "about 2.5x sooner".
- **Hardware/time [M, training/README, 2000 h HiFiTTS-2, effective batch 64, 24L teacher]:** requirements "One NVIDIA GPU (the default batch size wants ~56 GB; a consumer GPU runs `batch_size: 16` with `grad_accum_steps: 4` in ~16 GB)"; Linux only. Throughput table: 1xH100 6.3 steps/s (54 GiB), 8xH100 10.4 steps/s (12 GiB/GPU); to 400k steps 17.5 h (1xH100) or 10.7 h (8xH100); latent precompute ~50 min (1 GPU) / ~10 min (8 GPU) for 2000 h. Distillation (`depth_distill`, 200k steps): 5.3 h (1xH100) / 2.6 h (8xH100). Reference quality: 24L from scratch on 2,000 h: WER 0.94%, SIM 0.929, UTMOS 4.32; distilled 6L student WER 0.76%, UTMOS 4.35 (English, LibriSpeech test-clean).
- No A10/A10G numbers exist in the repo or issues. [U] for A10G speed.
- Open training issues: #198 (zero-shot voice-prompt training setup, open); #230 GPU inference.
- Other Kyutai statements: pocket-tts#118 (2026-04-08) the first multilingual 24L models were released before the 6L distillation because "The distillation process is a bit more painful than we expected"; Kyutai's multilingual data volumes per language are **not published** (user `aradix85` asked 2026-05-06; no maintainer answer found).

### 5.4 Commercial-use verdict (labelled)
- Code: all speech-relevant repos MIT/Apache: **commercial OK** [M].
- Weights: CC BY 4.0 (STT, Mimi, TTS, Pocket TTS): **commercial OK with attribution** on the face of the licence [M]; **non-commercial: hibiki-zero weights, Expresso/EARS voices**. Upstream training data includes NC/proprietary sources that Kyutai acknowledges (STT) or that are implied (TTS): **residual legal risk [U], needs a human legal view; not resolved by the licence label.** Under the project rule "use the more restrictive reading when labels conflict", treat Kyutai weights as *Tier-2 (risk-accepted)*, not Tier-1.

## 9. What adapting Kyutai STT to Telugu/Hindi would really require

Everything below is [E] unless cited.
1. **Tokenizer replacement + resized embeddings/heads.** Kyutai: "We'd need to change the tokenizer." Existing vocabularies are English or English/French. Non-Latin text under byte fallback explodes token counts (a third-party analysis in DSM#64: for non-Latin scripts "a single character can explode into multiple byte-level tokens, making the text and audio stream alignment impossible"). At **12.5 Hz (80 ms/frame)** each text token must be emitted within the time-aligned frames; Telugu/Hindi (long, agglutinative words, high syllable rate) are exactly the "fast-spoken/long-token" case Kyutai's own staff flagged as potentially needing a higher codec frame rate (DSM#171). Hibiki-Zero's workaround (adapt to a new input language with <1000 h, "Hibiki-Zero can also be adapted to a new input language with less than 1000h of speech data") is a different 3B model with **non-commercial weights**. [M]
2. **Word-level time-aligned transcripts** (not just utterance-level text): needs a forced aligner or Whisper timestamps. Whisper is unreliable for Telugu (project note on Whisper Telugu script collapse); a Telugu/Hindi CTC aligner or IndicConformer CTC alignments would be needed. Kyutai says "You can get time-aligned timescripts through Whisper if it supports your language well." [M]
3. **Data volume:** Kyutai: "a few thousand hours" and "we simply don't know what happens when you fine-tune on a language that wasn't included in pre-training" [M]. Our T1-only MVP data is ~1,280 h in total across three languages [project figure], i.e. ~400 h Telugu (Svanita used 451 h Telugu for an FastConformer fine-tune). Moshi precedent: J-Moshi used ~69-70k h mono pretraining + 344 h stereo FT [C, as quoted in moshi-finetune#21].
4. **Code:** no official trainer; the hack is jploski's patch (disable depformer/audio loss, mono input, 30 s windows, `ft_embed`) [C]; known issues: PAD collapse beyond 60 s, LoRA-merge friction, "extra_heads" mismatch for the VAD heads, no delay handling (the interleaver/delay must be built per Moshi paper section "Deriving streaming ASR and TTS", p16, as Laurent Mazare advised). **Unmaintained and unproven for non-Latin scripts.**
5. **Compute for a 1B full fine-tune:** bf16 weights ~2 GB; full FT with AdamW states + activations needs roughly 16-24 GB/GPU [E, very rough] so 8xA10 (24 GB) is plausible with gradient checkpointing; Kyutai's own STT fine-tune used 16 H100 for 100k updates at bs 128 (28k h). Throughput on A10 is unmeasured [U]. A "PoC in an hour or two" is only plausible for a *smoke test* that proves the loop runs (the jploski LoRA test took ~4 min on an L40S for 900 clips) and says nothing about Telugu accuracy.
6. **Runtime after training:** to hit the project gate (faster than real time on laptop CPU) the 1B model would need quantisation + a mobile/CPU runtime that does not exist for non-GGUF-ported forks: the best community CPU result is 8.4 fps (0.67x) on a 2024 Ryzen, so a **distilled smaller model** would be required, i.e. a new pre-training project (Kyutai's multilingual small STT base was announced in July 2025 and never released).
7. **Streaming semantics:** fixed 0.5 s (1B) or 2.5 s (2.6B) delay; Mideind's fine-tune needed 5 s. Telugu/Hindi would likely need a larger delay [E], which conflicts with a tight latency target.

## 11. Verdict

### (i) TTS: is "swap in Telugu data" realistic?
**Yes, with caveats.** Evidence: Kyutai's `training/` recipe (data prep, alignment, tokenizer, teacher, distillation) + `finetune_language.yaml`; Czech 976 h reaches 12% WER (Whisper judge) by 10k steps; a **Telugu** model exists from 124 h with 15k fine-tune steps + 53 h single-speaker distillation; Hindi (932 h from scratch) and Hindi/Hinglish (90 h) exist; CPU speeds 3-6x real time on one thread; ONNX/int8/int4 ports for browser/phones exist. **GPU time is hours on 8 GPUs; the real work is aligned, licence-clean Telugu data (+ a Telugu CTC aligner, which Meta MMS is not), tokenizer/EOS/punctuation fixes, a human listening evaluation, and licence clearance** (Kyutai base weights CC BY 4.0 with undisclosed multilingual data and NC-gated training corpora upstream; the Telugu author's IndicTTS/SYSPIN data terms are unlabeled on HF). Quality evidence is thin: Hindi 6L WER 23% under Whisper (vs 26.7% on real speech), the Telugu card publishes no metric, Korean 100M student "quite poor". Voice cloning degrades when distilling on one speaker (Telugu/Hindi syspin models are fixed-voice).
Minimal credible Kyutai-based TTS path: clean 100-300 h licence-safe Telugu (CC-BY-class) speech -> Telugu CTC aligner -> SentencePiece 4k -> `finetune_language.yaml` from the 24L English teacher (<=15-25k steps; ~0.5-1.5 h on 8 GPU class H100, longer on A10) -> `depth_distill` to 6L (or ship 12L/24L int8) -> listening test + CER via an Indic ASR -> int8/ONNX -> sherpa-onnx. [E]; budget days, not hours.

### (ii) STT: is "swap in Telugu data" realistic?
**No, not as a 1-2 hour PoC and not as a product path.** Evidence: no training code (Kyutai says it will not release any); only an unofficial patch with failure reports; only one public new-language fine-tune (Icelandic, Latin script, WIP, details undisclosed); Kyutai's own guidance is "a few thousand hours", a new tokenizer, and uncertainty about unseen languages, plus 12.5 Hz token-density issues that are worse for Indic scripts; and the model does not run in real time on x86 laptop CPUs (0.24x-0.67x, community alpha benchmark) nor on Android. A smoke-test fine-tune "works" in minutes (loop runs), which may be what the senior has in mind, but it proves nothing about Telugu WER.
Minimal credible Kyutai STT path (only if forced to try): `stt-1b-en_fr` + jploski patch on `moshi-finetune` (Apache-2.0), mono 30 s windows, new Telugu+Hindi+Latin SentencePiece (resize `text_emb`/`text_linear`), word-aligned T1 data (~1,000-1,300 h available vs "a few thousand" recommended), full FT on 8xA10 (memory [E], throughput [U]), accept >=2.5-5 s delay, then still need a distilled/smaller model for CPU. Expected: weeks of R&D with high risk; outcome not demonstrated by anyone.

### Why not Kyutai vs the NVIDIA FastConformer/Nemotron path (project's Path A/B)?
| Criterion | Kyutai STT | NVIDIA path (per `progress.md`) |
|---|---|---|
| Training code for new language | none official; hack | official NeMo recipes; Telugu/Hindi fine-tune of Parakeet-TDT shown on one RTX 5060 Ti (Svanita) |
| Hindi/Telugu at baseline | none | Nemotron-3.5: Hindi yes, Telugu no; IndicConformer/SraVaani exist as teachers |
| Streaming | yes (delay 0.5-2.5 s, fixed) | cache-aware streaming (Nemotron, lookahead-selectable) |
| Params / CPU | 1B-2.6B, 0.24-0.67x RT on x86 CPU (community) | ~0.1-0.6B, int8 ONNX via sherpa-onnx, designed for CPU |
| Android/iOS | iPhone MLX demo only | sherpa-onnx covers Android/iOS/RPi |
| Data need | thousands of hours + word alignments | utterance-level text suffices (RNNT/CTC) |
| Licence | CC BY 4.0 weights, NC data upstream | OpenMDW/NVIDIA licence (L-01 open) |
**Recommendation:** reject Kyutai for the STT deliverable (consistent with D-009, now with stronger evidence). If the company also needs on-device Telugu/Hindi **TTS**, Kyutai Pocket TTS is the best-supported open starting point (MIT code, CC BY 4.0 weights, official training code, CPU real-time, existing Hindi/Telugu community checkpoints to benchmark against), scoped as a separate project with its own data/licence work.
